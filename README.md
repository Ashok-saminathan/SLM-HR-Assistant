# Nimbus Works HR Policy Assistant - Small Language Model (SLM) project

A task-specific assistant that answers employee HR-policy questions with a **self-hosted small language model**
(`Qwen/Qwen2.5-1.5B-Instruct`, Apache-2.0) adapted with **LoRA / QLoRA**, optimised (merge, 4-bit NF4, batching) and
served through **FastAPI**. No hosted large-model API is used anywhere.

> The company, policies and questions are **synthetic** (fictional "Nimbus Works"). No private data is included.

## 1. Use case (Milestone M1)

| Item | Definition |
|---|---|
| Target users | Employees asking an HR helpdesk bot about leave, pay, benefits, conduct, travel policy |
| Input | One free-text question (5-500 chars) |
| Output | JSON `{"answer", "source", "answerable"}` - grounded in a retrieved policy excerpt, or a refusal |
| Why an SLM | Narrow task, short context, HR data should stay in-house, low latency / cost, fine-tunable on one free GPU |
| Success criteria (set **before** measuring) | valid-JSON >= 95%; task success given correct retrieval >= 85%; correct refusal of out-of-scope questions >= 80%; p95 latency <= 3 s at batch size 1 on a T4 |

## 2. System flow

```
User question -> Input validation (Pydantic) -> Retrieval (BM25 policy excerpt) -> Prompt build
  -> SLM inference -> Output validation (JSON schema, source in context) -> API response (or safe fallback)
  -> Logging & metrics (experiments/api/requests.jsonl, GET /metrics)
```

Three different things improve quality and are kept **separate and measured separately**:

| Lever | Where | How it is isolated in evaluation |
|---|---|---|
| Retrieval (RAG) - supplies the facts | `src/retrieval/` | `retrieval_hit_rate`, and `--mode oracle` (gold excerpt) vs `--mode retrieved` |
| Prompting - system prompt + JSON contract | `src/model/prompts.py` | The baseline uses the same prompt as the fine-tuned model |
| Fine-tuning (LoRA) - teaches format, grounding, refusal | `src/model/train.py` | baseline vs fine-tuned on identical test cases |

Fine-tuning does **not** memorise the policies; the facts come from retrieval. Fine-tuning teaches the model to reply in the JSON
format, to stay inside the excerpt and to refuse when the excerpt does not contain the answer.

## 5. Reproduce the main workflow (Milestones M3-M7)

```bash
python -m pytest -q tests                              # unit tests, no model needed
python -m src.data.build_dataset                       # M3: clean, dedupe, split (grouped by policy) -> reports/dataset_report.md
python -m src.model.baseline                           # M4: baseline outputs on validation prompts -> experiments/baseline/
python -m src.evaluation.evaluate --variant base --name baseline            # baseline on the held-out TEST set
python -m src.model.train                              # M5: LoRA fine-tune (validation only) -> artifacts/adapter, experiments/training/
python -m src.evaluation.evaluate --variant ft_lora --name finetuned_lora   # same test cases
python -m src.optimization.benchmark --variants ft_merged ft_merged_nf4 --batch-sizes 1 4   # M6: optimisation trade-offs
python -m src.evaluation.evaluate --variant ft_merged --name finetuned_oracle --mode oracle # retrieval vs model
python -m src.evaluation.report                        # M7: reports/benchmark_report.md (generated from measured files)
```
`scripts/run_pipeline.sh` runs all of it. For QLoRA set `method: qlora` in `configs/train.yaml`.
Seeds are fixed (`seed: 42`); for exact reproducibility also pin `model.revision` to a commit hash in `configs/model.yaml`.

### Rules followed
- The **test split is never read** by training or by any tuning step (`train.py` reads train + validation only; baseline prompts come from validation).
- Baseline is run and saved before any adaptation.
- Splits are grouped by policy, so test policies are unseen; `tests/test_data.py` checks for leakage.
- Data prep, retrieval, training, inference, evaluation and API code live in separate modules.
- No keys or private data in the repo; `artifacts/` (weights) is git-ignored - publish adapters to the Hugging Face Hub or a release.

## 6. Run the API (Milestone M8)

```bash
SLM_VARIANT=ft_merged uvicorn src.api.main:app --host 0.0.0.0 --port 8000     # docs at /docs
```
```bash
curl -s localhost:8000/ask -H 'content-type: application/json' -d '{"question":"How many sick days do I get?"}'
# edge case 1 - invalid input -> 422 {"error":"invalid_request",...}
curl -s localhost:8000/ask -H 'content-type: application/json' -d '{"question":"hi"}'
# edge case 2 - out-of-scope question -> answerable=false with the refusal text
curl -s localhost:8000/ask -H 'content-type: application/json' -d '{"question":"What is the weather in Chennai today?"}'
curl -s localhost:8000/metrics ; curl -s localhost:8000/health
```
Error handling: invalid input -> 422; model not loaded -> 503; unexpected error -> 500 without internals; model output that fails
validation -> HTTP 200 with a safe refusal and `"degraded": true` (unvalidated text is never returned).
Variants: `base`, `ft_lora`, `ft_merged`, `ft_merged_nf4` (CUDA), `ft_merged_int8_cpu` (CPU).

## 8. Known limitations
- Dataset is small and synthetic (test set = 20 cases), so differences of a few points are noise; extend `policy_kb.py` or plug in real (anonymised) FAQ data.
- BM25 top-1 retrieval can miss; retrieval misses are reported separately from model errors.
- Single-turn only; no authentication / rate limiting on the API (put it behind a gateway for real use).
- Policies are fictional - do not use for real HR decisions.
